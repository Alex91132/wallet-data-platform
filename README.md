# Wallet Data Platform — кошелёк от транзакции до решения

Сквозной проект по данным на предметной области электронного кошелька: от схемы OLTP с инвариантами денег
и тестов конкурентности до CDC-конвейера, хранилища, dbt-моделей и продуктовой аналитики с решением по A/B-тесту.
Одна задача — три роли аналитика: **системный** (требования, модель, API, контракты), **инженер данных**
(CDC, поток событий, ELT, качество данных) и **продуктовый** (воронки, удержание, эксперимент, инциденты).

                         CDC таблиц + outbox → domain.*

**Стек:** PostgreSQL 17 · Debezium 3.2 · Redpanda 25 (Kafka API) · ClickHouse 26 · dbt 1.12 (dbt-clickhouse) ·
FastAPI · Python · pytest · Plotly · Docker Compose. Данные синтетические: симулятор прогоняет полгода жизни сервиса
через те же функции, что и API, — 9,5 тыс. клиентов, 180 тыс. операций, полмиллиона событий.

## Что внутри — по ролям

### Системный аналитик

- [Требования](docs/system-analysis/requirements.md): цели и границы, роли, функциональные и нефункциональные
  требования со ссылками на реализацию, бизнес-правила (лимиты 115-ФЗ, комиссии, кешбэк), сценарии использования
  с альтернативными потоками (таймаут и повтор запроса, одновременные повторы).
- [Модель](docs/system-analysis/model.md): ER-диаграмма, конечные автоматы операции и заявки KYC, диаграмма
  последовательности перевода — от запроса до витрины, обоснование transactional outbox.
- [OpenAPI](docs/system-analysis/openapi.json) — генерируется из сервиса; денежные запросы требуют `Idempotency-Key`,
  повтор возвращает `200` и `Idempotent-Replayed: true`.
- [План трекинга и контракт событий](docs/tracking-plan.md) — JSON Schema с версионированием; нарушения — в DLQ с причиной.

### База данных и SQL

- **Инварианты денег — в схеме, а не в коде:** сумма проводок операции = 0 (deferred constraint trigger,
  проверка при `COMMIT`), `CHECK (balance >= 0)`, допустимые переходы статусов — триггером, одна заявка KYC
  на рассмотрении — частичным уникальным индексом, идемпотентность — `unique (initiator, idempotency_key)`.
- **Конкурентность** — [16 тестов](tests/test_concurrency.py): потерянное обновление, write skew и дедлок
  воспроизводятся, затем устраняются (`FOR UPDATE`, REPEATABLE READ, SERIALIZABLE, порядок блокировок);
  функции кошелька проверены на двойное списание, обход дневного лимита, встречные переводы и одновременные
  повторы. Тесты нашли реальный дедлок — `FOR UPDATE` против неявного `FOR KEY SHARE` проверки внешних ключей;
  разбор — в [concurrency.md](docs/concurrency.md).
- **Доступ:** сервис ходит под ролью без прав на таблицы (только `EXECUTE` функций с `SECURITY DEFINER`),
  аналитик видит ПДн только маскированными, кабинет мерчанта ограничен row-level security.

### Инженер данных

- **CDC без доработки сервиса:** Debezium читает WAL; ПДн отсекаются на источнике — публикация со списком
  столбцов (PostgreSQL 15+) и `column.exclude.list`. Доменные события — через transactional outbox и `EventRouter`.
- **ELT:** ClickHouse читает Kafka в «бронзовый» журнал изменений `raw.cdc_log` как есть (JSON);
  разбор, «последняя версия строки» и история — в dbt. Журнал хранит все версии, поэтому SCD2 строится
  без снапшотов (`dim_users_scd2`).
- **Поздние и повторные данные:** события из офлайна приходят через часы и дни, SDK повторяет отправку.
  Сырые доставки хранятся все (долю дублей можно измерить), дедупликация — по `event_id` в staging;
  `fct_sessions` — инкрементальная модель с водяным знаком по **времени приёма**, а не времени события.
- **Качество:** 49 моделей и тестов dbt — ключи, ссылки, допустимые значения и бизнес-тесты: баланс проводок
  в хранилище, остатки = сумма проводок, непересекающиеся интервалы SCD2, отсутствие ПДн в хранилище,
  SRM эксперимента; свежесть источников; [`reconcile.py`](scripts/reconcile.py) сверяет источник и хранилище
  до копейки.

### Продуктовый аналитик

[Отчёт](https://alex91132.github.io/wallet-data-platform/) отвечает на вопросы, ответы на которые аналитика
находит в хранилище, не зная параметров симуляции: какой канал приводит клиентов, которые платят и остаются;
помогла ли новая форма KYC и на каком шаге; окупается ли кешбэк 3 % (A/B с бутстреп-интервалами и решением);
когда и насколько упали платежи при сбое провайдера; кто похож на «дропа»; насколько можно доверять трекингу.

**Что нашла аналитика** (полгода, 9 549 регистраций, оборот покупок 72,8 млн ₽):

| Вопрос | Ответ |
|---|---|
| Какой канал приводит платящих клиентов | активация за 30 дней: рефералы 67 %, органика 57 %, реклама в соцсетях 26 %; удержание на 8-й неделе — 49 %, 37 % и 10 %. Кампания в соцсетях дала ~136 лишних регистраций и лишь ~33 платящих |
| Помогла ли новая форма KYC | доходимость 56 % → 69 % (ДИ не пересекаются); выигрыш целиком на шаге «селфи»: 70 % → 88 % |
| Окупается ли кешбэк 3 % | покупок +13 %, но «комиссии − кешбэк» на клиента 12,9 ₽ → −61,4 ₽ (ДИ разницы −79,1 … −69,5); после акции эффекта нет — **не раскатывать** |
| Что случилось 20.07 | сбой эквайера: 6 часов технических отказов до 36 %, не прошло 50 оплат |
| Есть ли мошенники | 7 «дропов»: пополнение и за 2 часа 5+ переводов круглыми суммами на свежие кошельки; все из одной рекламной волны, вывели 280 тыс. ₽ |
| Можно ли доверять трекингу | дублей 1 %, опоздавших событий 3 %, нарушений контракта 0,5 % — всё измеряется и учитывается |
| Сходится ли хранилище с источником | да, до копейки: число строк и суммы по операциям, проводкам и остаткам (`reconcile.py`) |

## Находки по ходу

Ошибки, которые поймали тесты и сверки, — и почему их стоит знать:

- **Дедлок при одинаковом порядке блокировок.** `FOR UPDATE` конфликтует с неявным `FOR KEY SHARE`, который берёт
  проверка внешних ключей при вставке операции; правильная блокировка для изменения остатка — `FOR NO KEY UPDATE`
  ([разбор](docs/concurrency.md)).
- **ClickHouse: псевдоним виден во всём `SELECT`.** `max(lsn) AS lsn` рядом с `argMax(payload, lsn)` даёт «агрегат
  внутри агрегата», а псевдоним `payload` в представлении затенил исходный столбец `payload`, и разбор JSON шёл уже
  по вложенному объекту. Правило: псевдоним не совпадает с именем столбца.
- **ClickHouse: `%` у `Decimal` работает с масштабированным значением.** `4018.00 % 1000` = `8`, поэтому проверка
  «круглая сумма» засчитывала всё, кратное 10, а признак антифрода не различал мошенников и обычных клиентов.
  Считать в целых копейках: `toInt64(amount * 100) % 100000 = 0`.
- **Дедупликация в бронзовом слое прячет проблему.** `ReplacingMergeTree` схлопывал повторные отправки событий,
  и доля дублей в отчёте была 0 при реальном 1 %. Сырой слой хранит все доставки, дубли убирает staging.

## Запуск

Нужны Docker и Python 3.12.

```bash
docker compose up -d --build                      # PostgreSQL, Redpanda, Debezium, ClickHouse, API
python -m venv .venv && .venv/Scripts/pip install -r app/requirements.txt dbt-clickhouse clickhouse-connect pandas numpy plotly pytest
.venv/Scripts/python scripts/bootstrap.py         # регистрация CDC-коннекторов
cd app && ../.venv/Scripts/python -m wallet.sim --days 182 && cd ..   # ~40 минут
cd dbt && ../.venv/Scripts/dbt run --profiles-dir . -s staging && cd ..   # представления для сверки
.venv/Scripts/python scripts/reconcile.py --wait 600                       # ждёт, пока CDC догонит источник
cd dbt && ../.venv/Scripts/dbt build --profiles-dir . && cd ..
.venv/Scripts/python scripts/report.py            # → docs/index.html
.venv/Scripts/pytest tests                        # тесты конкурентности (своя база wallet_test)
```

API с интерактивной документацией — http://localhost:8000/docs. Пароли в `docker-compose.yml` — только для локального стенда.
