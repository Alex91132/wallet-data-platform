# План трекинга и контракт событий

Клиентские события отвечают на вопросы, на которые OLTP ответить не может: где пользователь бросил онбординг,
сколько попыток оплаты не дошло до сервера, как часто открывают приложение. Деньги и статусы берутся из OLTP
(через CDC) — событие `purchase_started` означает намерение, а не покупку.

Контракт — [`app/wallet/contracts/app_event.schema.json`](../app/wallet/contracts/app_event.schema.json)
(JSON Schema 2020-12). Сборщик `/track` проверяет каждое событие: валидные — в топик `app_events`,
остальные — в `app_events_dlq` с причиной. В хранилище DLQ — таблица и витрина `mart_data_quality_daily`.

## Общие поля

| Поле | Тип | Зачем |
|---|---|---|
| `schema_version` | `"1.0"` | несовместимые изменения — только с новой мажорной версией |
| `event_id` | UUID | генерирует клиент; повторная отправка — тот же id → дедупликация в ClickHouse |
| `event_name` | перечисление | см. ниже; неизвестное имя — нарушение контракта |
| `user_id` | integer \| null | null до регистрации; обязателен у событий после входа |
| `anonymous_id` | строка | установка приложения — связывает поведение до и после регистрации |
| `session_id` | строка | сессия; сессии строит инкрементальная модель `fct_sessions` |
| `client_ts` | date-time | время на устройстве; событие может прийти через часы (офлайн) |
| `platform`, `app_version` | перечисление, семвер | сравнение версий: новая форма KYC вышла в 3.2.0 |
| `properties` | объект | поля конкретного события |

Время приёма (`received_at`) ставит сборщик, а не клиент: по нему работает водяной знак инкрементальной загрузки.

## События

| Событие | Когда | Свойства | Вопрос |
|---|---|---|---|
| `app_open` | старт сессии | — | DAU/WAU/MAU, липкость |
| `screen_view` | показ экрана | `screen` | путь по приложению, интерес к разделам |
| `signup_completed` | регистрация | `channel` | связка установки и пользователя |
| `kyc_started` | открыл форму KYC | `level` | доля начавших идентификацию |
| `kyc_step_completed` | прошёл шаг | `step` (passport / selfie / address), `form_version` | на каком шаге теряем; эффект формы v2 |
| `kyc_submitted` | отправил заявку | `level` | доходимость формы |
| `topup_started` | ввёл сумму пополнения | `amount` | брошенные пополнения (ушёл со страницы банка) |
| `purchase_started` | подтвердил оплату | `amount` | попытки, не дошедшие до сервера |
| `transfer_started` | подтвердил перевод | `amount` | — |
| `experiment_exposure` | увидел баннер эксперимента | `experiment_key`, `variant` | анализ по фактически увидевшим |

## Правила, которые проверяет контракт

- все обязательные поля на месте, лишних полей нет (`additionalProperties: false`);
- `app_version` — строго `X.Y.Z`; `amount` — больше нуля; `step`, `screen`, `variant` — из перечислений;
- у событий после входа есть `user_id`.

## Что делать с нарушениями

DLQ — не мусор, а сигнал: всплеск ошибок одного типа после релиза означает поломку трекинга в этой версии
приложения. `mart_data_quality_daily` показывает долю нарушений, дубли и опоздания по дням; в данных стенда —
около 0,5 % нарушений, 1 % дублей, 3 % сессий приходят с опозданием до трёх суток.
