# Кошелёк: требования

Документ системного аналитика: цели, роли, функциональные и нефункциональные требования, бизнес-правила
и сценарии использования. Реализация каждого требования указана ссылкой — требования проверяемы.

## 1. Цель и границы

**Цель.** Электронный кошелёк: клиент пополняет баланс, платит мерчантам с кешбэком, переводит деньги другим
клиентам и выводит их на карту. Данные о деньгах и о поведении в приложении попадают в аналитическое
хранилище для продуктовой, финансовой и антифрод-аналитики.

**В границах:** регистрация, идентификация (KYC), операции с деньгами, кешбэк, A/B-эксперименты, сбор событий
приложения, поставка данных в хранилище.
**Вне границ:** эквайринг и банк-партнёр (внешние системы, эмулируются), уведомления, служба поддержки.

## 2. Роли

| Роль | Кто | Что делает |
|---|---|---|
| Клиент | пользователь приложения | регистрируется, проходит KYC, пополняет, платит, переводит, выводит |
| Мерчант | магазин, кафе, такси… | принимает оплату, делает возвраты, смотрит свои операции в кабинете |
| Комплаенс | сотрудник | принимает решение по заявке KYC |
| Аналитик | продукт, финансы, антифрод | читает хранилище без доступа к открытым ПДн |
| Внешние системы | эквайер, банк | подтверждают пополнение и вывод; могут отказать (`provider_timeout`) |

## 3. Функциональные требования

| ID | Требование | Реализация |
|---|---|---|
| FR-1 | Регистрация по телефону создаёт клиента и его кошелёк; телефон и e-mail уникальны | `create_user`, `POST /users` |
| FR-2 | Клиент подаёт заявку KYC; одновременно на рассмотрении не больше одной заявки | `submit_kyc`, индекс `kyc_one_pending` |
| FR-3 | Решение по KYC повышает уровень идентификации; отказ — с причиной | `decide_kyc` |
| FR-4 | Пополнение, перевод, оплата, возврат, вывод проходят по правилам лимитов (раздел 5) | функции `topup`…`withdraw` |
| FR-5 | Каждый денежный запрос несёт ключ идемпотентности; повтор возвращает ту же операцию | `Idempotency-Key`, `unique (initiator, key)` |
| FR-6 | Отказ по бизнес-правилу — это операция со статусом `failed` и причиной, а не ошибка сервиса | `_finish(…, 'failed', reason)` |
| FR-7 | За покупку начисляется кешбэк отдельной операцией, связанной с покупкой | `purchase` → операция `cashback` |
| FR-8 | Мерчант видит в кабинете только свои операции | RLS-политика `merchant_own_ops` |
| FR-9 | Изменения статуса операции журналируются | `op_status_history` (триггер) |
| FR-10 | Доменные события публикуются надёжно: событие не теряется и не публикуется без изменения данных | transactional outbox → Debezium |
| FR-11 | Клиентские события проверяются по контракту; нарушившие попадают в отдельный поток с причиной | `/track`, `app_events_dlq` |
| FR-12 | Хранилище получает изменения OLTP без доработки сервиса и без открытых ПДн | CDC (Debezium), публикация со списком столбцов |

## 4. Нефункциональные требования

| ID | Требование | Как проверяется |
|---|---|---|
| NFR-1 | **Согласованность денег:** сумма проводок операции = 0, остаток не уходит в минус, остаток = сумма проводок | ограничения и deferred-триггер; `tests/`, dbt-тесты `assert_ledger_balanced`, `assert_balances_match_ledger` |
| NFR-2 | **Конкурентность:** параллельные запросы не создают двойного списания, обхода лимита и дедлоков | `tests/test_concurrency.py` (см. [concurrency.md](../concurrency.md)) |
| NFR-3 | **Идемпотентность:** повтор запроса (таймаут сети) не создаёт вторую операцию даже при одновременных повторах | `test_idempotency_under_concurrency` |
| NFR-4 | **Аудит:** любая операция восстанавливается по проводкам и истории статусов | `ledger_entries`, `op_status_history` |
| NFR-5 | **Защита ПДн:** в хранилище нет телефона, e-mail, ФИО, даты рождения; аналитик в OLTP видит их только маскированными | `users_masked`, dbt-тест `assert_no_pii_in_dwh` |
| NFR-6 | **Свежесть хранилища:** задержка CDC — секунды; dbt предупреждает, если данные старше 30 минут | `sources.freshness` |
| NFR-7 | **Полнота поставки:** число строк и суммы в хранилище совпадают с источником | `scripts/reconcile.py` |
| NFR-8 | **Поздние события** (офлайн-устройства) учитываются в сессиях и метриках | инкрементальная `fct_sessions` с перепроверкой по времени приёма |

## 5. Бизнес-правила

**Лимиты по уровню идентификации** (упрощённо по 115-ФЗ, таблица `kyc_limits`):

| Уровень | Остаток, не больше | Списания в день | Переводы людям |
|---|---|---|---|
| none — без идентификации | 15 000 ₽ | 15 000 ₽ | нельзя |
| basic — упрощённая | 60 000 ₽ | 60 000 ₽ | можно |
| full — полная | 600 000 ₽ | 600 000 ₽ | можно |

- «День» — календарный день по Москве; в дневной лимит входят покупки, переводы и вывод.
- **Комиссия мерчанта** — доля оплаты (0,8–2,5 % по категории), удерживается из суммы мерчанту; это доход сервиса.
- **Возврат** — не больше суммы покупки (суммарно по всем возвратам); доля комиссии возвращается пропорционально.
- **Вывод на карту** — только с идентификацией; комиссия 1 %, не меньше 50 ₽.
- **Кешбэк** — 1 % от покупки; в эксперименте `cashback_boost` группа test получает 3 % первые 30 дней после регистрации.
- **Причины отказа:** `insufficient_funds`, `daily_limit`, `balance_limit`, `recipient_limit`, `kyc_required`, `blocked`,
  `refund_exceeds_purchase`, `merchant_insufficient_funds`, `provider_timeout`.

## 6. Сценарии использования

### UC-1. Перевод другому клиенту

**Актор:** клиент. **Предусловие:** уровень KYC не ниже basic.

1. Клиент вводит получателя и сумму; приложение генерирует ключ идемпотентности и отправляет `POST /transfers`.
2. Сервис блокирует оба кошелька (по возрастанию id), проверяет статус, право на переводы, остаток,
   дневной лимит отправителя и лимит остатка получателя.
3. Сервис записывает операцию, две проводки, меняет остатки и пишет событие `operation.succeeded` в outbox — в одной транзакции.
4. Клиент получает `201` и статус `succeeded`.

**Альтернативы:**
- 2a. Правило нарушено → операция `failed` с причиной, `201` со статусом `failed`; деньги не двигаются.
- 1a. Ответ не дошёл (таймаут), клиент повторяет запрос с тем же ключом → `200`, `Idempotent-Replayed: true`, та же операция.
- 1b. Два повтора одновременно → второй ждёт фиксации первого на уникальном индексе и получает ту же операцию.
- 2b. Получатель не найден → `404`, операция не создаётся.

### UC-2. Оплата у мерчанта с кешбэком

1. `POST /purchases` с ключом идемпотентности.
2. Проверки: статус, остаток, дневной лимит; внешний эквайер может отказать (`provider_timeout`).
3. Проводки: клиент → мерчант (сумма), мерчант → счёт комиссий (комиссия); затем операция `cashback`:
   счёт кешбэка → клиент. Ставка кешбэка зависит от группы эксперимента.

### UC-3. Идентификация (KYC)

1. Клиент проходит шаги формы: паспорт → селфи → адрес (события `kyc_step_completed` с версией формы).
2. `POST /users/{id}/kyc` создаёт заявку `pending`.
3. Комплаенс принимает решение `POST /kyc/{id}/decision`; при одобрении уровень клиента повышается.
4. Отклонённый клиент может подать заявку снова.

### UC-4. Возврат по покупке

Мерчант инициирует `POST /refunds` по проведённой покупке. Сумма всех возвратов не больше покупки;
у мерчанта должно хватать средств.

### UC-5. Кабинет мерчанта

Мерчант подключается под ролью `merchant_portal`, сессия выставляет `app.merchant_id`; RLS отдаёт только его операции.
